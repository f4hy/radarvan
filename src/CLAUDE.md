# Frontend (`src/`)

- `Client.ts` configures the generated client (localhost:8000 in dev, Heroku in prod). MUI for components, recharts for charts. The generated client points at an **absolute** base URL, so it never sends the session cookie (cross-origin in dev) — anything cookie-authenticated uses a relative `fetch(..., {credentials: "same-origin"})` through the Vite proxy instead: `auth.ts`, `bracketApi.ts`, `voting.ts`, `mapUpload.ts`, `adminApi.ts`.
- The map component is named `GameMap` (from `src/Map.tsx`) to avoid shadowing the JS `Map` constructor. Pass `eventDots?: EventDot[]` to overlay dots in game-space coordinates.
- `ShowMatchDetails.tsx:EventChart` is pure MUI (no recharts); event types are driven by one `EVENT_TYPES` array (label, row, icon) — `EVENT_TYPE_BY_KEY` and `ROW_ORDER` are both derived from it, so adding an event type only means adding an entry there.
- recharts Sankey `nodePadding` is uniform across columns; `node`/`link` accept custom elements receiving layout props; `payload.sourceLinks` detects leaf nodes.
- Use `getColorHex`/`buildPlayerColorMap` from `src/utils.ts` for player-color maps; `WinRateRadar` is the shared radar chart (`data: {name, winRate}[]`).
- Format toggles: `FORMAT_OPTIONS` arrays drive ToggleButtonGroups; selected format goes up as the `gameFormat` query param; reset dependent state on format change.
- Static serving: a single `http_cache.CachedStaticFiles` mount (`html=True`, so `/` serves `index.html`). Hashed `/assets/*` are `immutable` for a year; `index.html` and the rest are `no-cache`, so deploys revalidate.
- `Bracket.tsx`'s `shortMatchLabel`/`ROUND_CODE` maps backend `round_name` strings (e.g. `"Winners Semifinal"`) to short card labels (`WSF-a`) — adding or renaming a round name in `bracket.py` (or a new `bracket_type`) needs a matching `ROUND_CODE` entry or it silently falls back to the raw name. `matchesById` and the hover-to-show-connector-lines callback are read via `useBracketData()` (`BracketDataContext`, mirroring `PlayerColorsContext`'s pattern) rather than threaded as props through `BracketNodeView`/`BracketTreeSection`/`LosersBracketColumns` — read from context in `MatchBox`, don't re-add prop drilling for a new cross-cutting concern there.
- `DebugData` (`?page=debug-data`) is gated on `useIsAdmin` (`status.user.is_admin`) — the old `?debug=True` flag is gone (see the comment on `AuthContext.useIsAdmin`).
- `AdminPanel.tsx` (`?page=admin-panel`, nav item gated on `useIsOpsAdmin`) is the ops control panel. Its tasks are **data, not JSX** — one `SECTIONS` array of descriptors drives rendering, validation, the request, and the result pane, so a new admin endpoint means adding an entry, not a component. A task marked with `confirmWord` stays disabled until the operator types that exact string (the match id, for the per-match deletes), and re-locks if the field it echoes changes. Requests go through `adminApi.adminRequest` (same-origin, cookie); the backend's `OPS_ADMIN` gate is the real boundary, the hidden nav item is not.
- **Matches filtering is server-side, and both endpoints take the same three params.** `player`/`mapName`/`gameFormat` go to `/api/dates` *and* `/api/matches/by_date` (`matches.filter_matches`), which is what keeps a night's headline count equal to the number of matches it expands to. The map value sent back is the stored string `/api/map_match_counts` returned (`maps/defcon6`), not the display name — `displayMapName` is only the Autocomplete's label. Night rows are keyed on the filter set so a night already expanded refetches instead of showing what it loaded under the old filter. Nights paginate at `NIGHTS_PER_PAGE`; the page counts ~400 of them.
- **Two forms of the general icon, two of the map image.** `DisplayGeneral` is the avatar plus its name badge (the common case); `GeneralAvatar` is the bare, sizable logo, for rows and headers that already write the name and would collide with a badge. Likewise `GameMap` is the full article (overlay dots, supply tooltip, a 300px floor) and `MapThumbnail` is just the picture, lazily loaded — the one to use in a list of eighty rows.
- **Map Stats has a reader-side games floor on top of the backend's.** `map_stats.MIN_GAMES` (5) is the server's; the `Min games` toggle is the browsing aid over it, and **search deliberately ignores it** — someone who typed a map's name wants that map however thin it is. A best/worst badge click pins its map past the floor rather than scrolling to a row that isn't rendered, so the scroll waits a render (`scrollTo` state, not an inline `scrollIntoView`).
- **Match details is a tab strip with the first tab open**, not a toggle group over an empty panel. `Displays` strings stay the switch keys; `DISPLAY_LABELS` only shortens what a tab shows.
- **Two bars, and they answer different questions.** `WinRateBar` fills by *rate*, so 3-0 and 30-0 draw the same bar; `WinLossVolumeBar` sets the bar's *length* by games played and splits it by result, for where sample size is the point. Its `max` comes from the set being compared — Player Stats scales to that player's own busiest general, because per-general counts run 110 down to 3 and a page-wide max leaves half the roster with slivers.
- **One fact, one encoding.** Player Stats used to render each general's win rate three times per player (list chip, bar-chart label, radar point). Its vertical bar chart is gone, but the sample size it alone carried moved into the rows — a rate with no sense of how many games are behind it is the thing this page is easiest to misread. The rows are where you read a number, the radar is where you see the shape; don't add a third panel that answers neither better.

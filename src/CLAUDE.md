# Frontend (`src/`)

## End-to-end tests (`e2e/`)

- **`npm run test:e2e` — Firefox, no backend, no database.** The API is served from typed fixtures through `page.route` (`e2e/mockApi.ts`), and `playwright.config.ts`'s `webServer` builds and previews the production bundle. The division is deliberate: pytest owns server behaviour (`tests/test_spa_fallback.py` covers the SPA fallback these URLs depend on), vitest owns pure functions, and this owns what only a browser can answer — routing, real links, error states, cache behaviour and keyboard operation.
- **Fixtures are typed against `src/api`** (`e2e/fixtures.ts`), so a backend model change fails `tsc -p tsconfig.e2e.json` instead of drifting until a test goes red for an untraceable reason. `tsconfig.e2e.json` is separate because e2e needs Node globals and `src` must not: browser code reaching for `process` should stay a type error.
- **A fixture must be complete, not minimal.** Omitting `started_at` from the game-night recap made `clockSpan` call `new Date(undefined).toISOString()`, and the page threw "invalid date" into its error boundary. That is a bug in the fixture, not a discovery about the app.
- **`mockApi` records unmocked paths and the smoke test asserts there are none**, so a page that starts calling a new endpoint fails loudly rather than silently receiving `null`.
- **Register `mockApi` *before* a per-test override.** Playwright matches routes in reverse registration order, so a catch-all added last swallows the specific route you meant to test.
- **`expectNoErrorBoundary` is not redundant with the console check.** A caught render error is *handled* — the boundary draws a panel and the shell survives — so a test that only waits for an `<h1>` can pass on the frame before the throw.
- **The calendar keyboard test waits for `networkidle` on purpose.** `react-activity-calendar` renders `<Suspense fallback={renderedBlock}>` around a lazily-loaded Tooltip, so for the first few hundred milliseconds the *uncloned* element is on screen with its handlers intact, and only after the chunk lands does `cloneElement` spread floating-ui's props over them. Without that wait the test passes against a calendar whose keyboard support breaks moments later — verified by running it against the broken build in both directions.

## Lint and types

- **The linter is on: `recommended` plus Biome's `react` domain.** It used to be `"rules": {"preset": "none"}` with about twenty hand-picked rules and nothing React-specific — so the one class of mistake this codebase actually makes, a wrong `useEffect` dependency array, was the one thing not checked. `biome.json`'s override now carries only deliberate *deltas* from recommended; anything that merely restated a default is gone.
- **`useExhaustiveDependencies` runs with `reportUnnecessaryDependencies: false`.** The missing-dependency half catches real stale-closure bugs and is an error. The unnecessary-dependency half fights a legitimate idiom — the reset effect (`useEffect(() => setFailed(false), [basename])`), whose whole purpose is to re-run when a value changes that its body never reads. Removing those deps would break the effects. Don't turn that half back on to "be thorough"; it would ask you to delete working code.
- **A `biome-ignore` needs its reason on one line.** A wrapped `//` continuation silently makes the suppression inert — Biome then reports both the original diagnostic *and* `suppressions/unused`, which is the tell.
- **`noArrayIndexKey` is an error, and the exceptions are written down.** The dangerous cases were fixed with real keys (bracket seed rows hold an editable Autocomplete each — an index key rebinds that input to the wrong row when a seed is removed; bracket tree nodes; team partitions). What remains is genuinely positional — fixed-length skeletons, a split string rendered in place, a win/loss streak — and each carries a one-line justification, `biome-ignore-all` at the top where a whole file is the same case.
- **`noUncheckedIndexedAccess` is still off**, deliberately: it produces 88 errors and is its own piece of work. `verbatimModuleSyntax` is on and cost nothing.
- **Standing warnings are judgment rules** (`noNonNullAssertion`, `noExplicitAny`, `noAccumulatingSpread`) — visible in review, not blocking. Errors are the bug-catching rules, and there are currently none.

## Data fetching

- **Every read goes through TanStack Query.** `queryClient.ts` holds the one cache; `App.tsx` provides it. There is no `useFetch` any more, and no page fetches in a `useEffect`. Before this the app had four different fetch idioms across 26 files, no cache (so the router unmounting a page meant refetching it from scratch on every navigation), no deduplication, no retry and no cancellation.
- **`staleTime` is 60s to match the backend, not by taste.** `@derived(on=CORPUS)` revalidates its corpus token on a 60s DB poll, so an answer younger than that is one the server would have recomputed from identical inputs. `queryClient.test.ts` pins it.
- **`QueryState` renders the error branch, so a call site can't forget it.** It takes a query and a render prop, and hands `children` a non-nullable `data`. Use `queryFallback(query, what)` instead only where the component's own hooks depend on the data (a `useMemo` over the rows) and so must sit above any conditional return.

  This replaced a convention — `data === null` meant loading — that had no room for "failed" at all: an errored request left the page in its skeleton forever, and on `PlayerStats`, `PlayerSynergy`, `GeneralStats` and `Superlatives` the early `return <Loading />` sat *above* the JSX that mounted the error snackbar, so the failure reached nobody. Don't reintroduce a page-local `loading`/`data === null` pair.
- **`apiError.errorMessage` is what makes an error readable.** The generated runtime throws `ResponseError` with the fixed text "Response returned an error code"; this pulls FastAPI's `detail` (string, or a validation list) off the body. `apiError.test.ts` covers it.
- **`BILLED_QUERY_OPTIONS` is not optional on the two endpoints that cost money.** A cache *miss* on `GET /api/matchup_commentary/` or `GET /api/bracket_summary/{id}` generates, billing a real LLM call. The query client's defaults would re-ask on window focus — someone tabbing back to a bracket popup would silently spend money — so both spread `BILLED_QUERY_OPTIONS`, which turns off refetch-on-focus/mount/reconnect and retry, and holds the answer for the session. `queryClient.test.ts` asserts each flag. Stale flavor text is free; a refetch is not.
- **A read gets an error panel; a write gets a snackbar.** `useErrorSnackbar` survives for mutations only (voting, linking bracket games, admin actions) — a user action failing has nothing on screen for an error state to replace. Where a write returns the updated resource, put it in the cache with `setQueryData` rather than invalidating and refetching what the server just told you.
- **Two `useEffect`s that are still correct to keep:** genuinely imperative, button-driven fetching. `DebugData` ("type a match id, press Submit") and the Draft/Balance Teams randomize actions are commands, not views of state — a `useQuery` there would fetch as you type. Leave them.
- **`ErrorBoundary` is the backstop for a render-time throw**, which `QueryState` can't catch. One wraps the routed page in `Menu` (keyed on the path, so navigating away clears it) and one wraps the whole app in `App.tsx` with a plain-DOM fallback, since the theme may be what failed. Before this, one bad field on one card blanked the entire app, nav included.

## Routing

- **`routes.tsx` is the one list of pages** — slug, title, icon, nav heading, gate and lazy component in a single entry. It drives the router (`App.tsx`), the sidebar and the app-bar title, so adding a page means adding one entry. It replaced five parallel lists (an `ALL_SELECTIONS` union, a block of `React.lazy` bindings, a `NavGroup[]`, a 25-arm `switch`, and inline gate conditions) that could disagree with each other. A route's `title` is also the string its `Page` renders as `<h1>` — nav and page can't drift.
- **URLs are paths (`/game-night?date=…`), and the server has to cooperate.** `http_cache.CachedStaticFiles.get_response` serves `index.html` for any non-`/api`, non-`/assets` path that isn't a real file. Without it a hard refresh or a pasted link 404s. `/api` keeps its JSON 404 on purpose (a client parsing HTML as JSON fails confusingly, and `main.handle_http_exception` reports 401/403 from that path space); `/assets` keeps its 404 because a miss there means a stale `index.html` naming a build that's gone, and HTML would surface as a console syntax error instead. `tests/test_spa_fallback.py` holds all of that.
- **`?page=` links still work and must keep working.** The app routed on that query param for years and those links are meant to be pasted into chat, so they exist in Discord scrollback forever. `App.tsx`'s `LegacyPageRedirect` translates one into its path form, carrying `date`/`player`/`player1`/`player2` across, and `replace`s so it isn't a Back step. An unknown `?page=` value falls through to Matches rather than the not-found screen — it is likelier a renamed slug than a typo, and the visitor didn't write the link. Route slugs are therefore not free to rename.
- **Navigation is links, not handlers.** Nav items are `ListItemButton component={NavLink}`, and `PlayerChip`/`PlayerLabel` are `component={Link}` with an href from `links.ts` — so ⌘-click, middle-click and "copy link address" all work, and the sidebar's active styling reads off `NavLink`'s own `.active` class (same signal as the `aria-current="page"` it sets). Build hrefs with the `links.ts` helpers rather than template strings: `URLSearchParams` is what stops a name like `pc | purple` from truncating the URL. `usePlayerNav()` is the imperative escape hatch for the few non-link call sites; it replaced `PlayerNavContext`, which only existed because `Menu` used to own the routing state.
- **A query param that matters is `useUrlParam`, not `useState`.** Pages used to hold `useState(playerFromUrl)` beside a `setPlayerInUrl` helper — two copies of one fact, seeded once at mount. That was a live bug: clicking a player chip while already on Player Profile changed the URL and not the page, and Back/Forward did the same. `useUrlState.ts` makes the URL the only copy. It pushes by default (Back should return to the previous player); pass `{ replace: true }` for a value that changes continuously or for a default the page writes in itself (Game Night's landing on the latest night).

- **The generated types lie about dates inside dict-valued fields.** The generator emits a per-item `FromJSON` for a plain `Array<Model>` (which is why `BracketTournamentOutput.matches` gives real `Date`s) but passes a `{ [key: string]: Model }` or `{ [key: string]: Array<Model> }` straight through — no converter runs on the values. `PlayerRatingData.playerRatingOvertime` is the live case: `atdate` is declared `Date` and arrives as a **string**. Wrap it (`new Date(x.atdate ?? 0)`), as the rest of `PlayerRatings.tsx` already does; a call site that trusts the type typechecks and then throws `toISOString is not a function` on the page. `apiError.test.ts` pins both halves of this, and `e2e/fixtures.ts`'s `PLAYER_RATINGS` deliberately populates that field so the smoke test exercises it.

- **`Client.ts` is the one client, and its `basePath` is `""` — keep it relative.** Every generated path already starts with `/api`, so a relative base is same-origin in both environments (dev: the Vite proxy; prod: the single FastAPI process that also serves `dist/`), and `credentials: "same-origin"` therefore carries the session cookie. API-key and cookie-session routes both go through it. MUI for components, recharts for charts.

  It used to be an **absolute** base URL (localhost:8000 / the Heroku host), which made every dev request cross-origin and the cookie unsendable — so `auth.ts`, `bracketApi.ts`, `voting.ts` and `mapUpload.ts` each grew a parallel hand-written `fetch` *and a hand-written snake_case copy of the response types*, unchecked against the backend. Those copies are gone; all four now re-export the generated models. Restoring an absolute base path brings the whole parallel layer back.

  Two deliberate exceptions. `mapUpload.uploadMaps` still hand-builds its request: the generator emits `useForm = false` for `/api/map_upload`, so its method would send the files as a `URLSearchParams` body — it uses the generated *types* and `MapUploadResponseFromJSON`, just not the generated request. `adminApi.adminRequest` stays a generic path+method helper because `AdminPanel`'s `SECTIONS` array is data, not one call site per endpoint; it declares no types of its own.

- **Sending an API key on a cookie route is fine.** `_require_logged_in_admin` treats a normal-tier key as "not an admin key" and falls through to the cookie check, and the session routes don't declare APIKeyHeader — so the one client can carry both credentials without either gate misfiring.

- **Errors go through `apiError.errorMessage`.** The generated runtime throws `ResponseError` with the fixed text "Response returned an error code"; `errorMessage` unwraps FastAPI's `{"detail": …}` (string or validation list) off the response. `useErrorSnackbar`'s `showError` calls it, so every page got real error text out of the migration. `responseErrorMessage(resp)` is the same thing for `mapUpload`, which holds a `Response` rather than a thrown error.

- **Dates are `Date`, not ISO strings.** The generated converters parse `scheduled_at`/`reveal_at`, so `bracketFormat`'s `formatScheduledAt`/`useCountdownMs` and Agenda's `onSchedule` all take `Date`. `useCountdownMs(null)` returns `NaN` on purpose — `remaining <= 0` is false for `NaN`, which is what keeps an unscheduled match's prediction poll open (it used to be spelled `new Date("")` at the call site).

- **The generated models are stricter than the hand-written copies were**, mostly `T | null | undefined` where the copy said `T | null`. Compare with `== null` / `!= null`, not `=== null`: `match.winner !== null && match.winner === match.playerA` was true for an unplayed match where both were `undefined`, which would have drawn player A as the winner. `AuthStatus.user` likewise arrives as `undefined` for a null user, so the logged-out test is `!status.user`.
- The map component is named `GameMap` (from `src/Map.tsx`) to avoid shadowing the JS `Map` constructor. Pass `eventDots?: EventDot[]` to overlay dots in game-space coordinates.
- `ShowMatchDetails.tsx:EventChart` is pure MUI (no recharts); event types are driven by one `EVENT_TYPES` array (label, row, icon) — `EVENT_TYPE_BY_KEY` and `ROW_ORDER` are both derived from it, so adding an event type only means adding an entry there.
- recharts Sankey `nodePadding` is uniform across columns; `node`/`link` accept custom elements receiving layout props; `payload.sourceLinks` detects leaf nodes.
- Use `getColorHex`/`buildPlayerColorMap` from `src/utils.ts` for player-color maps; `WinRateRadar` is the shared radar chart (`data: {name, winRate}[]`).
- **`MatchActivityCalendar`'s two nested `<g>`s are load-bearing.** `react-activity-calendar` wraps whatever `renderBlock` returns in its own Tooltip, which does `cloneElement(children, { ref, ...getReferenceProps() })` — floating-ui's props are spread *after* yours, so anything it also sets is silently replaced. It sets `onKeyDown` and `ref`; it does not set `onClick`. A single `<g>` therefore gave a calendar that worked with a mouse and did nothing on Enter, with no error anywhere. The outer `<g>` is the sacrificial one it clones; put anything interactive on the inner one.
- Format toggles: `FORMAT_OPTIONS` arrays drive ToggleButtonGroups; selected format goes up as the `gameFormat` query param; reset dependent state on format change.
- Static serving: a single `http_cache.CachedStaticFiles` mount (`html=True`, so `/` serves `index.html`). Hashed `/assets/*` are `immutable` for a year; `index.html` and the rest are `no-cache`, so deploys revalidate.
- `Bracket.tsx`'s `shortMatchLabel`/`ROUND_CODE` maps backend `round_name` strings (e.g. `"Winners Semifinal"`) to short card labels (`WSF-a`) — adding or renaming a round name in `bracket.py` (or a new `bracket_type`) needs a matching `ROUND_CODE` entry or it silently falls back to the raw name. `matchesById` and the hover-to-show-connector-lines callback are read via `useBracketData()` (`BracketDataContext`, mirroring `PlayerColorsContext`'s pattern) rather than threaded as props through `BracketNodeView`/`BracketTreeSection`/`LosersBracketColumns` — read from context in `MatchBox`, don't re-add prop drilling for a new cross-cutting concern there.
- `DebugData` (`/debug-data`) is gated on `useIsAdmin` (`status.user.isAdmin`) — the old `?debug=True` flag is gone (see the comment on `AuthContext.useIsAdmin`).
- `AdminPanel.tsx` (`/admin-panel`, nav item gated on `useIsOpsAdmin`) is the ops control panel. Its tasks are **data, not JSX** — one `SECTIONS` array of descriptors drives rendering, validation, the request, and the result pane, so a new admin endpoint means adding an entry, not a component. A task marked with `confirmWord` stays disabled until the operator types that exact string (the match id, for the per-match deletes), and re-locks if the field it echoes changes. Requests go through `adminApi.adminRequest` (same-origin, cookie); the backend's `OPS_ADMIN` gate is the real boundary, the hidden nav item is not.
- **Matches filtering is server-side, and both endpoints take the same three params.** `player`/`mapName`/`gameFormat` go to `/api/dates` *and* `/api/matches/by_date` (`matches.filter_matches`), which is what keeps a night's headline count equal to the number of matches it expands to. The map value sent back is the stored string `/api/map_match_counts` returned (`maps/defcon6`), not the display name — `displayMapName` is only the Autocomplete's label. Night rows are keyed on the filter set so a night already expanded refetches instead of showing what it loaded under the old filter. Nights paginate at `NIGHTS_PER_PAGE`; the page counts ~400 of them.
- **Two forms of the general icon, two of the map image.** `DisplayGeneral` is the avatar plus its name badge (the common case); `GeneralAvatar` is the bare, sizable logo, for rows and headers that already write the name and would collide with a badge. Likewise `GameMap` is the full article (overlay dots, supply tooltip, a 300px floor) and `MapThumbnail` is just the picture, lazily loaded — the one to use in a list of eighty rows.
- **Map Stats has a reader-side games floor on top of the backend's.** `map_stats.MIN_GAMES` (5) is the server's; the `Min games` toggle is the browsing aid over it, and **search deliberately ignores it** — someone who typed a map's name wants that map however thin it is. A best/worst badge click pins its map past the floor rather than scrolling to a row that isn't rendered, so the scroll waits a render (`scrollTo` state, not an inline `scrollIntoView`).
- **Match details is a tab strip with the first tab open**, not a toggle group over an empty panel. `Displays` strings stay the switch keys; `DISPLAY_LABELS` only shortens what a tab shows.
- **Two bars, and they answer different questions.** `WinRateBar` fills by *rate*, so 3-0 and 30-0 draw the same bar; `WinLossVolumeBar` sets the bar's *length* by games played and splits it by result, for where sample size is the point. Its `max` comes from the set being compared — Player Stats scales to that player's own busiest general, because per-general counts run 110 down to 3 and a page-wide max leaves half the roster with slivers.
- **One fact, one encoding.** Player Stats used to render each general's win rate three times per player (list chip, bar-chart label, radar point). Its vertical bar chart is gone, but the sample size it alone carried moved into the rows — a rate with no sense of how many games are behind it is the thing this page is easiest to misread. The rows are where you read a number, the radar is where you see the shape; don't add a third panel that answers neither better.
